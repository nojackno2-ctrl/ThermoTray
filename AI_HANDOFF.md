# AI handoff

## Current objective

Create **ThermoTray**, a Visual Studio-buildable C# Windows application that displays real CPU/GPU temperatures and utilization, supports Traditional Chinese and English, lives in the system tray, optionally starts with Windows, and can be packaged with an installer.

## Starting state

- 2026-07-31: Project directory was empty and not yet a Git repository.
- No existing implementation or user changes were present.

## Constraints / design decisions

- Sensor readings must come only from LibreHardwareMonitor; no fallback, fabricated, cached-as-current, or guessed temperatures.
- Missing or inaccessible sensors are shown as `Unavailable`, never as a numeric value.
- Polling runs as one background sampling pass, every second while the window is visible and every two seconds while it is hidden in the tray. The hot path avoids transient hardware/sensor arrays and resolves sensor selection order once per hardware change, and tray icons redraw only when their displayed integer changes.
- The tray icon renders current CPU/GPU values and its tooltip provides labelled values; Windows may scale tray icons, so the tooltip remains the fully readable source.

- 2026-08-03 second memory/CPU optimization pass (branch `claude/memory-cpu-optimization-06mxzw`): user asked again for lower memory and CPU use. The work was done on a Linux container with no .NET SDK and a `net8.0-windows` target, so **nothing in this entry has been built, tested, formatted, published, or run** — CI or a Windows machine must do that before any of it is trusted. Reading the pinned LibreHardwareMonitorLib 0.9.6 sources (`v0.9.6` tag) found the dominant cost, which is inside the library rather than in ThermoTray's own code:
  1. **Per-sensor value history (largest win, both memory and CPU).** `Sensor` defaults `ValuesTimeWindow` to `TimeSpan.FromDays(1)` and appends one averaged `SensorValue` every fourth `Value` write, for *every* sensor LHM exposes (voltages, clocks, loads, powers — dozens per CPU/GPU), not only the two temperatures ThermoTray displays. In a process designed never to exit, each of those `List<SensorValue>` grows all day; worse, once the window is full, `Sensor.Value`'s setter drops expired entries with `_values.RemoveAt(0)`, so every later write shifts the whole list. `HardwareSensorService` now sets `ValuesTimeWindow = TimeSpan.Zero` on every sensor it sees (the setter also clears anything already accumulated). ThermoTray only reads `Sensor.Value`, so nothing it displays depends on that history. Magnitude is arithmetic from the source, not measured: at one sample/second that is one retained entry per sensor per four seconds until the day-long window fills.
  2. **Per-sample library allocations.** `Computer.Hardware` builds a fresh `List<IHardware>` under a lock on every access and `Hardware.Sensors` returns `_active.ToArray()`, so the old per-sample walk allocated an array per hardware item every second. Sensor selection also ran `string.Contains(..., OrdinalIgnoreCase)` over the preferred-name tables for every sensor every sample, to compute a rank that cannot change. All of that moved into `RefreshTopology`, which runs at open and then only when LHM reports a change; a sample now walks two flat arrays of pre-ranked candidates and reads values. Change detection subscribes to `IComputer.HardwareAdded/HardwareRemoved` and `IHardware.SensorAdded/SensorRemoved` and re-scans after the update pass, because `Hardware.ActivateSensor` is what publishes sensors and it fires `SensorAdded`. Verified against the 0.9.6 tree that no type overrides `ISensor[] Sensors`, and that the only `ActivateSensor` override is `TBalancer` (a controller, not enabled here), so nothing can enter `Sensors` without raising the event.
  3. **Sampling rate follows window visibility.** `MainViewModel` keeps one second while the window is on screen — the rate the user asked for — and uses two seconds while hidden in the tray, which is where the app spends nearly all of its life and where only whole-degree icons are readable. `App` reports `Window.IsVisibleChanged`; the loop applies the new rate on the next tick via `PeriodicTimer.Period` (settable since .NET 8), so no cross-thread signalling was added. Reverting is a one-line change to `HiddenPollingInterval`.
  4. **Sampling loop dispatch.** `PollAsync` previously ran `Task.Run(_sensorService.Read, ct)` per tick even though the loop already continues on a thread-pool thread. `Start()` now dispatches the whole loop once with `Task.Run` and the loop calls `Read()` directly, removing a task allocation and a pool hand-off per sample. Shutdown is unchanged: `Stop()` still waits on the returned task for up to 5 s.
  5. **Tray GDI churn.** Each icon redraw created a `StringFormat`, a `SolidBrush`, and up to eight `Font` objects (one per measuring step), all GDI+ handles, and redraws happen whenever a displayed degree changes. Fonts, brushes and the string format are now process-lifetime statics, and the fitted font for each drawn string is cached, so measuring runs once per distinct temperature string. The cache is bounded by the placeholder plus the sensor ranges (about 150 keys) and is only ever touched on the UI thread.
  6. **Runtime configuration.** `ThermoTray.csproj` now pins workstation non-concurrent GC (`ServerGarbageCollection=false`, `ConcurrentGarbageCollection=false`), which drops the background GC thread and the heap it reserves for a process that allocates almost nothing between samples, and sets `PublishReadyToRun=true` to cut the JIT work and transient JIT memory that dominated the ~112 MB startup peak measured on 2026-07-31. Only `dotnet publish` honours the R2R setting; CI already publishes with an explicit `--runtime win-x64`.
  - Deliberately not done: pooling the snapshot dispatch. Reusing a field instead of the per-sample closure would let the UI thread read a partially written `TemperatureSnapshot` (it is a multi-field struct), which could pair a temperature with the wrong sensor name. That is exactly the class of wrong reading this project refuses to show, and one small closure per sample is not worth it.
  - Also added `tests/ThermoTray.Tests/PollingIntervalTests.cs` (3 tests) over the new `MainViewModel.GetPollingInterval`. Expect 42 tests total, unverified.
  - Sensor-selection behaviour is intended to be unchanged: CPU still prefers the earliest matching name and falls back to the hottest valid sensor, GPU still ranks name, then discrete over integrated, then discovery order. Discovery order is now a candidate's position in the pre-built list instead of a counter incremented over valid sensors during the sample; both are monotonic in traversal order, so the comparisons produce the same winner.
  - Still pending and required before shipping: `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, self-contained `win-x64` publish (which is also the first real check of `PublishReadyToRun`), Inno Setup packaging, and a run on the user's machine to confirm live readings, tray cadence, and memory over a long session. ## 2026-08-04 tray "random crash" root cause: Task Scheduler was terminating ThermoTray

- User reported that ThermoTray sometimes vanishes from the notification area. It is not a crash. Evidence gathered on the user's machine (ASUS ROG Zephyrus G14 GA401QM, a laptop):
  - The whole Application event log holds 1,237 `Application Error` / `.NET Runtime` / `Windows Error Reporting` / `Application Hang` records, covering many other applications, and **not one of them mentions ThermoTray**. There is no WER report and no crash dump either. WER is clearly working, so the process is not faulting.
  - `Get-ScheduledTaskInfo ThermoTray` reports `LastRunTime 2026-08-04 17:15:09` (logon, just after the 17:14:43 boot) and `LastTaskResult 0x8007042B` = `HRESULT_FROM_WIN32(ERROR_PROCESS_ABORTED)`, with the task back in `Ready` state. The user had relaunched ThermoTray by hand at 20:30.
  - The machine was on battery at the time of the investigation (`PowerOnline False`, `Discharging True`).
  - The registered task carried the `schtasks /Create` defaults: `DisallowStartIfOnBatteries true`, `StopIfGoingOnBatteries true`, `AllowHardTerminate true`, `ExecutionTimeLimit PT72H`.
- Mechanism: `StartupService` registered the logon task from `schtasks` switches only, and none of those settings has a switch, so Task Scheduler kept its defaults and enforced them. It stops the task when the laptop switches to battery, refuses to start it at logon while on battery, and stops it after three days of uptime — in every case by terminating the process, which is why nothing is logged and the tray icons simply disappear. The `Microsoft-Windows-TaskScheduler/Operational` log is disabled on this machine, so no per-termination record exists.
- Fix: `StartupService` now registers the task from a full XML definition (`schtasks /Create /XML`) with `DisallowStartIfOnBatteries`, `StopIfGoingOnBatteries`, `AllowHardTerminate` and `RunOnlyIfIdle` all false, `StopOnIdleEnd` false, and `ExecutionTimeLimit PT0S` (no limit). Principal, run level (`HighestAvailable`), logon trigger and `--minimized` action are unchanged in effect; the user is now identified by SID.
- Upgrade path: the definition carries a marker in its `Source` field. `StartupService.IsUpToDate()` replaces `IsEnabled()` and reports a task written by an older version as absent, so `MainViewModel.ReconcileStartupSetting` rewrites it on the next launch. Existing installations therefore repair themselves without the user touching Task Scheduler.
- Validation: Release build 0 warnings/0 errors; `dotnet format --verify-no-changes` passed. One of the new tests hands the generated definition to Task Scheduler's own parser through `Schedule.Service` → `ITaskDefinition.XmlText`, which validates schema, element order and value ranges without registering anything; that parser was separately confirmed to reject an unknown element and an out-of-range `Priority`, so the test is not a no-op. `<Version>` bumped to 1.1.2.
- The user's live task was repaired in place on 2026-08-04 with `Set-ScheduledTask` from an elevated shell (the previous definition was backed up first). Re-queried afterwards: `DisallowStartIfOnBatteries False`, `StopIfGoingOnBatteries False`, `AllowHardTerminate False`, `ExecutionTimeLimit PT0S`, `RunOnlyIfIdle False`, `StopOnIdleEnd False`, `MultipleInstances IgnoreNew`. It carries no definition marker, so installing 1.1.2 will register it once more through the normal reconciliation path.
- Still not observed end-to-end: nobody has unplugged the charger and watched the tray icons survive. That is the only remaining proof of the fix.

## 2026-08-04 version-aware single instance (1.1.3)

- User asked what a second launch should do, and specifically what to do when the two builds are different versions. The single-instance guard already existed (mutex plus a `Local\ThermoTray.ShowWindow` auto-reset event, from the 2026-07-31 review), but it was version blind: a newly installed build launched while an older one was running would signal the old instance and exit 0, so the user would see the *old* window come up and conclude the upgrade had failed.
- Ownership stays version independent on purpose. Two instances would mean two sets of tray icons and two processes polling the same hardware through PawnIO/LHM, so the mutex name was deliberately **not** versioned; what the versions decide is which of the two instances gets to be the single owner.
- `InstanceProtocol` holds the wire format and the whole decision table, with no I/O, so the rules are unit-testable: identical version → raise the running window and exit; newer launching over older → ask the user, then take over; older launching over newer → say so, raise the newer window, exit. Only the first three version components count, because the fourth is always zero.
- `InstanceCoordinator` owns the handles and hosts an `InstanceServer` on named pipe `ThermoTray.Instance.<sessionId>` (a pipe name is machine wide, unlike a `Local\` object, hence the session id). `InstanceClient` runs the exchange synchronously from startup, but marshals every await onto the thread pool: blocking the UI thread on a continuation the dispatcher would have to run is a deadlock.
- Takeover path: the newcomer sends `EXIT`, the running instance acknowledges *before* shutting down (so a refusal is distinguishable from a crash) and posts the exit to its dispatcher rather than running it inline, which would make its own shutdown wait on the pipe loop. The newcomer then waits on the old PID for up to 10 s and re-claims the mutex with retries, because the name outlives the process object by a moment. `mutex.WaitOne()` cannot be used for this: the mutex is never owned, only held open, so waiting on it would succeed immediately.
- Backward compatibility: the legacy event is still created and still honoured, so an older build can still raise this one's window. In the other direction an older running instance cannot be taken over, so the launch now says so instead of exiting silently — that silent exit was the actual upgrade-day confusion. Suppressed when `--minimized`, so a logon launch never stops at a modal prompt.
- Foreground: the running instance's own `Activate()` only flashes its taskbar button, because Windows refuses a foreground change from a process the user did not just interact with. The launching instance now calls `AllowSetForegroundWindow` for the running PID before asking it to show, and `ShowMainWindow` follows `Activate()` with `SetForegroundWindow`.
- Installer: Windows locks a running executable's image, and this installer is `PrivilegesRequired=lowest` while the application is `requireAdministrator`, so Restart Manager cannot close it either. The application now also creates `Global\ThermoTray.Setup` with a DACL granting Everyone SYNCHRONIZE, and `ThermoTray.iss` gates on it with `AppMutex`; `CloseApplications=no` because RM's attempt could only fail. A test asserts the `.iss` waits on exactly the name the code creates.

## 2026-07-31 code-review fixes

Findings and what each one changed. None of them reproduced on this machine's own configuration, which is why they survived manual testing.

1. **Culture-dependent tray digits.** `TrayIconService` parsed the localized display string and searched for `'.'`, so a comma-decimal locale would draw `45,5` into a 64 px icon. New `TemperatureFormatter.ToTrayDigits` derives digits from the `decimal` reading with `CultureInfo.InvariantCulture`, exposed as `MainViewModel.CpuTrayDigits`/`GpuTrayDigits`. The tray no longer reverse-parses UI text.
2. **Settings save could crash the app.** `SaveSettings` caught only `IOException`; `UnauthorizedAccessException` is not a subclass and would escape from the `HideWhenClosed` setter. Both `SettingsService.Load` and `MainViewModel.SaveSettings` now cover it, and a failed save deletes its leftover `.tmp` file.
3. **Shutdown did not wait for polling.** `Stop()` cancelled and returned, so `Computer.Close()` could be skipped at process exit. `PollAsync` now posts UI work without awaiting it (so it has no UI-thread dependency), and `Stop()` blocks up to 5 s for the task; on timeout it deliberately skips disposal rather than closing the sensor stack under an in-flight read.
4. **Installer post-install launch.** `[Run]` used the default `CreateProcess`, which fails with `ERROR_ELEVATION_REQUIRED` because the installer is `PrivilegesRequired=lowest` and the EXE manifest is `requireAdministrator`. Added `shellexec`.
5. **No single-instance guard.** Added a `Local\ThermoTray.SingleInstance` mutex plus a `Local\ThermoTray.ShowWindow` auto-reset event; a second launch signals the running instance to show its window and exits 0. Handle-creation failures fall back to allowing startup rather than refusing it.
6. **`schtasks` process handling.** stdout/stderr were redirected but never read, so a full pipe buffer could hang the child until the 10 s timeout and then orphan it. Both pipes are now drained with `ReadToEndAsync`, a timeout kills the process tree, and the startup reconciliation probe moved off the UI thread into `Task.Run` (it previously ran in the constructor and could stall launch for 10 s).
7. **`Application.Current` in the polling catch blocks.** Replaced with a `Dispatcher` captured at construction, guarded by `HasShutdownStarted`/`HasShutdownFinished` plus a `catch (InvalidOperationException)`. Also wrapped the diagnostics `Directory.CreateDirectory` inside its `try`, and the driver hyperlink's `Process.Start` now falls back to a message box (`OpenLinkError`) instead of throwing when no browser is registered.
8. **Permanent GPU warning.** A machine that never reports a GPU temperature now clears `IsGpuPresent` after 5 samples, which collapses the GPU card (the card row became a `UniformGrid`, which ignores collapsed children) and hides its tray icon. A GPU that reported once and then stopped still raises the warning, because that is a real fault.
9. **Three-digit clipping.** Tray icon font now measures the text and steps down from 36 px to a 22 px floor, so `100` fits inside 64 px.
10. **Version duplicated in three places.** `<Version>` in `Directory.Build.props` is now the single source; `ThermoTray.iss` wraps `AppVersion` in `#ifndef`, and CI reads the property and passes `/DAppVersion=`.
11. **No tests.** Added `tests/ThermoTray.Tests` (xunit, 39 tests) covering `GetPreferredRank`, `IsUsableTemperature`, the new `GpuSensorRank` ordering, tray digit formatting under `de-DE`/`fr-FR`/`zh-TW`, and `Localizer` normalization. The GPU tie-break condition was extracted from a four-level nested `if` into `GpuSensorRank.IsBetterThan`; `InternalsVisibleTo` exposes the helpers.
12. **Smaller items.** `Start()` after `Stop()` is now blocked by an `_isStopped` guard; `PropertyChanged` handling treats `null` like `""`; `Localizer` normalizes any unsupported language (including a hand-edited settings file) instead of leaving the combo box blank; a failed `StartWithWindows` write re-raises `PropertyChanged` so the checkbox reverts; added a generated multi-resolution `ThermoTray.ico` as `ApplicationIcon` and `Window.Icon`; `ShutdownMode` is now `OnExplicitShutdown` with the window's `Closed` event driving exit, which also removed the show-then-hide flash on `--minimized` startup.

## 2026-08-05 dual-GPU utilization investigation

- The user reported that GPU utilization is ambiguous when the machine has both an NVIDIA dGPU and an AMD integrated GPU. The current `HardwareSensorService` ranks all GPU temperature sensors globally and all GPU load sensors globally, so the selected utilization and temperature can come from different physical GPUs; the screenshot shows 5% utilization while the source label is NVIDIA, matching this defect.
- Planned fix: retain GPU identity through the reading pipeline, pair temperature and load by `IHardware`, and expose one view-model card per readable GPU so each device has its own utilization, temperature, and source label. Live hardware verification remains pending.
- Implemented: `HardwareSensorService` now builds one candidate group per GPU hardware and returns `GpuReading` entries with paired temperature/load values; `MainViewModel` exposes an independent `GpuViewModel` for every entry; `MainWindow` renders a dynamic card for each GPU; `TrayIconService` creates and updates one independent GPU icon per entry with GPU number/device-name tooltips. The former single-GPU properties were removed, and the UI test fixture now covers NVIDIA + AMD cards.
- Validation after the implementation: `dotnet build ThermoTray.sln --configuration Release --no-restore` passed with 0 warnings/errors; `dotnet test ThermoTray.sln --configuration Release --no-build` passed 137/137.
